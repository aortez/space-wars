# NES reference provenance and reproduction

`engine-nes` is a Rust-native implementation. It does not build, link, or ship
the C reference runtime, SDL, or pthread code. The optional tools under
`tools/nes-reference` compile against a separate DirtSim checkout solely to
regenerate behavioral evidence.

The Rust CPU is independently structured around the documented 6502 bus
sequences. It is not a line-by-line translation of SmolNES. DirtSim remains an
important oracle, but a mismatch is investigated against hardware behavior
rather than automatically copied.

## Reproducing the DirtSim capture

The host needs GCC or Clang, SDL2 development files, `pkg-config`, pthreads,
and optionally GDB. Start from clean checkouts:

```sh
git clone https://github.com/aortez/dirtsim.git /tmp/dirtsim-nes-reference
git -C /tmp/dirtsim-nes-reference checkout 0db5f847e7c059b807eb982702ba26fe9f004bf9
curl -fL \
  https://raw.githubusercontent.com/xram64/falling-nes/52dcb8a951200562e696dfc2aba5d4d14edd0078/falling.nes \
  -o /tmp/falling-52dcb8a9.nes
sha256sum /tmp/falling-52dcb8a9.nes
tools/nes-reference/capture-dirt-sim.sh \
  /tmp/dirtsim-nes-reference /tmp/falling-52dcb8a9.nes
tools/nes-reference/trace-dirt-sim-startup.sh \
  /tmp/dirtsim-nes-reference /tmp/falling-52dcb8a9.nes
```

The capture creates fresh runtimes for frames 1, 2, 10, and 100, then runs a
fixed input script:

```text
frames 1..100    neutral
frame 101        Start held
frames 102..130  neutral
frames 131..150  Right held
frames 151..170  neutral
```

It hashes RGB565 output, palette indices, CPU RAM, PRG RAM, a bounded PPU
snapshot, and the runtime savestate using FNV-1a 64. The checked-in output is
[`tests/reference/falling-smolnes-0db5f847.txt`](tests/reference/falling-smolnes-0db5f847.txt).
The C utility is optional provenance tooling, not a test dependency.

## CPU startup comparison

Generate the Rust trace with:

```sh
cargo run --release -p engine-nes --example cpu_trace -- \
  /tmp/falling-52dcb8a9.nes 20
```

Both cores reset to `$C006`, execute the same first eleven instructions, call
the helper at `$C000`, and then repeat `BIT $2002` / `BPL $C000`. That is the
first expected dependency on the not-yet-implemented PPU: the placeholder
status register never enters vblank.

The Rust trace prints status values `$20` higher than DirtSim. Bit 5 is an
unused status bit which reads/pushes high on 6502 hardware. SmolNES stores and
prints it low internally. The Rust core deliberately normalizes it high, so
this explained trace difference is retained rather than emulating a reference
representation detail.

The compact comparison is checked in as
[`tests/reference/falling-startup.txt`](tests/reference/falling-startup.txt).

## Benchmarks

The DirtSim artifact records an initial full-machine comparison on an AMD
Ryzen 7 9800X3D host. It is not directly comparable to the current CPU-only
Rust benchmark because DirtSim also clocks the PPU and optionally APU and
converts frames. Full-machine comparisons begin after those devices exist.

Run the allocation-free generated CPU workload with:

```sh
cargo run --release -p engine-nes --example cpu_benchmark -- 10000000
```

`tests/no_allocation.rs` wraps the system allocator only in its test process
and asserts that 10,000 steady-state CPU instructions allocate, reallocate,
and deallocate nothing.

The example emits two versioned newline-delimited JSON objects containing
crate/profile, OS/architecture, API/workload version, configuration,
instruction and cycle counts, elapsed time, throughput, and a deterministic
RAM signature. `instruction-step-v1` measures the synchronous instruction API;
`cycle-scheduler-v1` measures the lower-level path that exposes every CPU/DMA
scheduler slot for later PPU/APU integration.

On the reference host, the instruction path initially runs at roughly 90 MHz
of emulated CPU bus clocks (about 34 million generated-loop instructions per
second). The fully observable cycle scheduler initially runs at roughly 56
MHz. Those are about 50x and 31x the 1.79 MHz NTSC CPU clock respectively,
before PPU/APU work is added. Keeping both rows makes abstraction cost visible
instead of folding it into a single favorable number.

Performance numbers are evidence tied to a host and workload, not acceptance
goldens. The instruction/cycle counts and RAM hash are deterministic; elapsed
time is not.

## Optional official-opcode conformance run

The external canonical `nestest` ROM and log were also run locally from
[`christopherpow/nes-test-roms@97720008e51db15dd281a2a1e64d4c65cf1bca4c`](https://github.com/christopherpow/nes-test-roms/commit/97720008e51db15dd281a2a1e64d4c65cf1bca4c).
They are not redistributed or required by CI.

```text
nestest.nes sha256=f67d55fd6b3cf0bad1cc85f1df0d739c65b53e79cecb7fea8f77ec0eadab0004
nestest.log sha256=442c4dd5539c7e88b3fd73c7b732a7eadbd22b47c2cd9e58397ef147f64f6f8f
```

Run a local copy with:

```sh
cargo run --release -p engine-nes --example cpu_nestest -- \
  /path/to/nestest.nes /path/to/nestest.log
```

The 2026-08-17 run matched all 5,003 official-opcode trace entries, including
PC, A/X/Y, status, stack pointer, and cumulative cycles through cycle 14,579.
The runner stops when the canonical log enters its starred unofficial-opcode
section, which is deliberately outside this slice.
